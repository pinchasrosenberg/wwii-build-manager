# Game stack evaluation — living WWII simulation

Research date: **2026-09-27**. Status: **provisional architecture decision; implementation and performance are untested**.

## Recommendation

Use **Godot 4.7.2 + its core OpenXR interface** as the provisional desktop/VR stack, with an isolated **typed domain/data simulation module inside Godot**. The same engine/backend runs it without presentation in headless mode. Future transfer to VR is an explicit product requirement. Godot's documented PCVR and standalone Android/Quest routes materially change the earlier Bevy-first recommendation. The technical evidence and migration contract are in [VR_READINESS.md](VR_READINESS.md). This selects the spike candidate; it is not a claim of measured performance or completed headset compatibility.

The product must first feel like a compelling place to inhabit: movement, companions, atmosphere, readable orders, meaningful work and consequential decisions. Historical grounding governs what the world claims; it does not replace play. A technically excellent headless simulation that produces a lifeless scene fails this evaluation.

**Godot has a material advantage in integrated scene/animation authoring and a core XR lifecycle. Unity is the strongest fallback for a standalone-XR interaction/tooling bottleneck; Unreal is a serious alternative when PCVR character/environment production dominates.** Bevy remains a credible Rust-first challenger: its community XR work is real and now targets Bevy 0.19 on the development branch, but matching manifests does not establish an end-to-end supported headset stack. Preserve headless, provenance and deterministic context guarantees regardless of presentation engine.

Do not build a bespoke renderer over wgpu at this stage. It would turn a game production task into an engine production task. Fyrox has a useful native Rust editor and headless support, but no current supported XR route was verified; it cannot be the baseline for the new VR requirement without that proof.

## Provisional stack and boundaries

1. **Canonical simulation:** isolated typed GDScript data classes/functions with explicit integer ticks, stable domain IDs, ordered commands, scoped RNG streams and versioned state. Domain code has no camera, rendering, UI, live input, audio or Deliver dependencies; use internal ports for physics/navigation. Runtime Godot data types may be used internally, while persistent contracts use explicit portable schemas and stable IDs rather than engine instance IDs or scene paths. [Static typing](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/static_typing.html)
2. **Presentation:** Godot scenes, AnimationTree, input and audio through adapters; core OpenXR owns the VR camera/session path. M1 stays in one engine and language/toolchain path. Pin engine/export templates and prove ordinary Android ARM64 export; no Rust/GDExtension/native-library gate is imposed on the initial slice.
3. **Physics:** Godot/Jolt for local interaction through the same adapter in rendered and live-headless execution; the domain module owns accepted consequential outcomes. This removes a second physics implementation, but does not prove deterministic physics. Test live replay in its pinned determinism domain, and separately test event replay from recorded authoritative outcomes. Avian/Rapier remain alternatives for a Bevy challenger.
4. **Navigation:** begin with Godot's local navigation behind a query/result adapter. Bake a small tile-based mesh and test obstacle/link/formation behavior. Tactical route cost, formation, acknowledgement and social spacing are distinct systems. Planetary precision does not solve navigation.
5. **World:** domain geospatial coordinates plus cell-local render/physics positions. Conversion records CRS, units, origin and transform version. Stream cells by manifest; keep far-away simulation aggregated rather than creating a rigid body for every historical object.
6. **Characters:** deterministic behavior trees, utility rules and authored dialogue are valid first implementations. Personality can arise from persistent preferences, knowledge, needs, relationships and animation/audio response. A language model is optional and cannot be required by the simulation clock.
7. **Network:** local authoritative simulation first; preserve a commands/snapshots/events interface. Select Godot or a transport-neutral network adapter only when multiplayer enters scope. Lightyear applies to a Bevy challenger, not implicitly to Godot. Account/session authorization is separate from entity replication.
8. **Assets:** author in external tools and export an interoperable format such as glTF. Each asset has an ID, content hash, license, source/author, historical status and uncertainty/reconstruction sidecar. Beauty is produced through composition, material, lighting, sound and animation; provenance metadata alone does not create it.

**Engine-neutral contracts are required; an engine-free executable is not required in M1.** Godot documents GPU-free headless operation and GDScript supports static typing. No evidence found in this review makes Rust necessary for a small slice. Mandatory FFI would add binding, native-library packaging, Android ABI and replay integration work before a measured benefit. Keep Rust as an optional later extraction for a profiled hotspot, larger headless scale or an actual external-consumer requirement. Extract one port-backed module with unchanged schemas and parity fixtures; if native code is introduced, desktop/Android packaging and binding-version checks become mandatory then. [Headless operation](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html)

Across every candidate:

- **HistoricalTruth** is a versioned, read-only evidence snapshot. **Reconstruction** contains explicit spatial/temporal assumptions and alternatives. **Gameplay** contains rules, invented moments and player consequences. A gameplay result cannot promote itself into historical truth.
- The game engine must not import **Deliver internals** or the existing research/UI implementation. It reads published, versioned scenario/context contracts through an adapter. A test should reject forbidden dependencies.
- Reusable capabilities are data-defined (`move`, `observe`, `carry`, `communicate`, `maintain`, `rest`, `assist`), with declared preconditions, effects, costs, permissions and schema versions. Avoid one-off systems that only work for a named battle.
- A deterministic scoped context contains the scenario revision, truth/reconstruction revision IDs, cell/time scope, role/knowledge filters, permitted capabilities, ordered entity IDs, input hashes and a budget. No entire historical corpus is implicitly loaded into a character or process.
- Experience profiles may alter assistance, interface, recovery and lethality. They do not rewrite source claims, historical identity or evidence quality. Any counterfactual outcome stays in Gameplay with its initiating commands.

## What “deterministic” must mean

Use separate guarantees rather than one marketing label:

| Guarantee | Required scope | Proof |
|---|---|---|
| Command replay | Same pinned build, content, seed and ordered commands reproduce canonical state and event hashes. | Headless versus rendered, repeated process runs, different render frame rates. |
| Save / resume | Restoring a snapshot and replaying remaining commands matches an uninterrupted run. | Checkpoint at a known tick; compare later canonical hashes. |
| Cross-platform canonical logic | Integer/fixed-point domain decisions match across declared supported targets. | Matrix run on at least two target architectures before claiming support. |
| Detailed physics | Initially a declared determinism domain: exact backend/toolchain/features/platform. | Record conditions; test collisions and insertion order. Broader guarantees require additional proof. |
| Recorded-outcome replay | Domain module consumes previously accepted physics/navigation/external-decision events. | Compare canonical state/event hashes without rerunning those external calculations; this does not prove live physical determinism. |
| Presentation | Camera, particles, interpolation and audio mixing may differ without altering authority. | Vary presentation timing and inspect canonical hashes. |

Fixed timesteps alone do not establish determinism. Sort authority-changing operations by stable IDs; define RNG algorithm/seed/stream; isolate wall-clock and I/O; apply asynchronous results only through sequenced accepted events. Record any external character decision before it affects play. Asset arrival and task completion order must not decide outcomes. Preserve content hashes and schema/migration versions in saves and replay headers.

Rapier documents local determinism and conditional cross-platform determinism, including initialization order, feature selection and math constraints. Those conditions apply to Rapier, not automatically to Avian, Fyrox's pinned integration, or the complete game. [Rapier determinism](https://rapier.rs/docs/user_guides/rust/determinism/)

Prefer authoritative server snapshots and recorded commands/events over promising full-world lockstep. Keep irreversible domain effects outside non-authoritative particles/ragdolls. If detailed physics materially changes a domain outcome, its accepted result must be captured or covered by the replay contract.

## Measured spike: game first, engineering gates underneath

These are **proposed acceptance thresholds**, not observations or benchmarks. Declare hardware, OS, resolution, engine/package versions, graphics settings, entity definitions and fixture hashes before running. Adjust a target only with a recorded reason; do not move the target after seeing a failure.

### A. Playable presence slice — primary product gate

Build one **15–20 minute** locally playable sequence: arrival at a small position, orientation, movement with **3–5 squad companions**, a meaningful quiet activity, a clear order, a route/priority choice, and a consequence the player can perceive. Historical setting and grounded constraints must be reviewed; invented conversations and specific moment-to-moment staging remain Reconstruction/Gameplay. A scene full of evidence panels is not the acceptance artifact.

Required elements:

- Responsive walk, stop, turn, crouch and interaction with stairs, doors and slopes; no mandatory head bob, camera shake or motion blur. Controls can be remapped and assistance adjusted.
- Companions acknowledge an order through behavior and a readable audiovisual cue; follow, wait, regroup and task behavior have visible transitions. A companion needs persistent identity and a reason to act, not an LLM.
- At least two quiet activities, for example checking equipment and moving supplies, affect preparedness, time, trust or route choice. Their purpose and result must be legible without a developer explanation.
- Layered environmental sound, distance cues, footsteps matched to ground, purposeful lighting, animation transitions, gaze and small idle behavior. Use polished representative assets in a small area; do not require a giant content library.
- A readable objective and optional journal/orders view; source detail is available on demand. Subtitles and cues must remain readable in the selected game language, including a Hebrew/RTL text test.
- An interruption or uncertain report makes the player choose. Feedback distinguishes what the character knows from what the underlying scenario knows.

Review the following **quality vector independently** on a 1–5 scale: `historical`, `visual`, `simulation`, `character`, `interaction`, `atmosphere`, `interest`, `coherence`, `performance`. A 1 means the dimension blocks the experience; 3 means coherent and playable with visible shortcomings; 5 means convincing for the slice. Use scores diagnostically; a high average must not hide a failed dimension. Historical review also requires an expert evidence audit.

The first formative gate matches [EXPERIENCE_DESIGN.md](EXPERIENCE_DESIGN.md): **at least three unfamiliar testers**, all able to describe their role and one consequence, **at least two wishing to continue**, and no blocking control/readability failure. Observe quiet tasks and orders without live coaching. These are formative signals, not statistically representative market validation. Record friction and consented quotes; no playtest is claimed in this document.

A 20 Hz domain scheduler does not force 20 Hz rendering or physics. Detailed local physics can run at a separate fixed rate, with deterministic synchronization points and render interpolation. Slow-changing strategy records can update less often using an explicitly defined simulation LOD; transitions must preserve conserved quantities and entity identity.

### C. Comparison and decision rule

Start with Godot and the required VR seams. A competing engine earns a comparison slice when a concrete limitation emerges; use the same locality, assets, interaction script, companion behavior, target headset/runtime and capture path. Reuse exported domain fixtures, not engine internals. Compare implementation effort, visible quality, frame-time distribution, on-device portability and maintenance risk. Avoid unsupported weighted scores.

Retain Godot if it passes the game, domain-isolation/headless and VR gates. Prefer Unity if its supported XR interaction/vendor packages remove a measured blocker; consider Unreal for demonstrated PCVR art/animation gains. Bevy can replace Godot only after an exact compatible XR stack passes the same device/export/lifecycle gates and materially improves the project's work. Fyrox/custom wgpu require a verified XR route before reconsideration. No candidate is cleared for a VR release without target-device testing.

Failure to resolve compatible Bevy navigation/world packages is a real schedule cost. Options are a tested older coherent Bevy set, a small owned adapter, or another engine; choose explicitly after measuring. “Latest” is not more valuable than a reproducible coherent set.
